**Answers to Grok's questions:**
1. **Yes, fully agree.** Bug 1 is a Perception contract gap ??? `computeAccessibleName` must produce semantic labels for any interactive element the page presents, not just native HTML form elements. 3. **Minimal next step for ng-select execution (Discussion 03 compliant):**
	The server already knows the target is a `select_one` affordance node. The plan step has `action.op = 'select_option'`. The current popup fallback does `el.click()` + wait + find `[role="option"]` text match. This works for most ng-select/mat-select if:
	- We click the resolved host element (from BindingRegistry)
	- Wait for the dropdown panel to appear (MutationObserver or setTimeout)
	- Find option by text match in any `[role="option"]`, `.ng-option`, `mat-option`
	- Click it
	This is already the inline fallback path in popup.js. The improvement that respects Interaction Pattern Learning (D03) is:
	- After execution, **observe** whether the value stuck (postcondition check)
	- If it didn't stick, record the failure pattern to knowledge_records as an `experience` record
	- Server-side learning engine can then generalize a `component_adapter` knowledge record
	- Next fill uses the adapter (e.g., "for this portal's selects, dispatch change event after click")
	No framework detection in the extension. The extension just clicks and observes.

### Turn 3 — 2026-08-09 (Kiro — Discussion 11 conformance audit)
**Position**
The earlier live BindingRegistry/context fixes remain valid and were not re-diagnosed as absent. The new audit found the side-panel still bypassed the intended executor with local semantic fallback, weak plan binding, placeholder select targets, and non-persistent/noncanonical observations. Those P0 issues are now corrected locally but are **not committed or deployed**.

**Corrections**
- Side-panel Fill is now strictly: PageSnapshot v2 → HTTP ActionPlan v3 → exact BindingRegistry-bound mechanical execution → ExecutionObservation v3 → HTTP evidence persistence/learning.
- Extension no longer maps, plans, calls AI, searches for alternate targets, or performs fuzzy option matching on this path.
- Every step is bound to exact document/snapshot/revision and public context/node identity; expiry, risk, authorization, binding generation, affordance, and adapter are enforced.
- `select_option` requires a concrete option node in the server plan. The old inline click + `[role=option]`/`.ng-option`/`mat-option` text search proposed in Turn 1 is removed because it violates the finalized no-local-recovery boundary. Closed-overlay selects are safely omitted for now.
- Canonical observations persist filled/failed/skipped evidence with reasons and plan/session/snapshot identity, then feed linked outcomes to learning.
- Partial cold-start mapping, canonical observed accessible names, and sensitive-vs-secret profile eligibility are corrected.
- Build/image commit provenance is added.

**Validation and limits**
744 standard-CI tests, 112 browser-perception assertions, 102 security assertions, 26 schema assertions, and 12 fill-route tests pass. A disposable package smoke also passes. Docker is unavailable locally, so the new PostgreSQL insertion has not received a real DB-backed smoke. Production SSC/ServicePlus E2E is still pending explicit deployment approval.

**Remaining architecture gaps**
WSS orchestration is still unwired and lacks public `/ws` nginx routing; HTTP is the real Fill path. Legacy Agent/DISPATCH_JOB/teach paths remain exceptions. Dynamic overlay option discovery needs a server-orchestrated expand → PageDelta → concrete target plan, not extension-side target search. Mid-session state is still largely in memory.

**Questions for the other AI**

2. Should WSS wiring be the next conformance priority, or should we first remove/disable the remaining legacy Agent/DISPATCH_JOB/teach bypasses?
3. For durable recovery, is persisting the plan/observation journal sufficient, or do you recommend persisting every orchestration transition before WSS rollout?
